# Рабочие правила для Claude (проект Vokal)

Файл читается автоматически при старте сессии. Здесь — правила процесса и
продуктовый контекст.

## Продукт

**Vokal Director** — русскоязычный AI-музыкальный директор: берёт готовую песню и
готовит её к репетиции группы или к уроку музыки.

- **Работа пользователя.** Загрузил песню → выбрал сценарий и цель → получил
  `Stage Pack`: партии, аккорды, MIDI, аудиослои, минус, клик, репетиционные
  треки, список мест для проверки и предложения AI-директора.
- **Для кого.** Кавер-группы и музыкальные руководители; преподаватели музыки и
  школьные ансамбли. Не массовое B2C.
- **Отличие.** Рынок занят отдельными утилитами (убрать вокал, разделить stems,
  найти BPM, распознать аккорды). Vokal делает цельный процесс
  «песня → состав → играбельная аранжировка → пакет к репетиции → правки после».
- **Собственное ядро.** `SongGraph`, Arrangement Engine, Pedagogy Engine,
  Confidence and Review Engine, Version Engine, правила выдачи, `DirectorAction`
  DSL. Готовые модели берём на stems, транскрипцию, beat tracking и LLM.

Подробности: `docs/mvp.md`, `docs/architecture.md`, `docs/songgraph.md`,
`docs/roadmap.md`, `docs/research-notes.md`.

## Стек

- **Фронтенд:** Vite + React 19 + TypeScript (strict), обычный CSS с токенами в
  `src/styles.css`, иконки `lucide-react`.
- **Тесты:** Vitest. Сервисные тесты — в окружении `node`, компонентные —
  `jsdom` + `@testing-library/react` (окружение задаётся докблоком в файле).
- **Платформа:** web (SPA). Целевой backend ещё не выбран — развилка
  NestJS / FastAPI описана в `docs/architecture.md`.
- **Текущий статус:** моковый инкремент. Реальной обработки аудио, backend, авторизации
  и платежей нет — см. «Что пока не работает» в `README.md`.

## Коммуникация

- **Claude ведёт разработку сам.** Батчи берём по WSJF-приоритету автономно, без
  спроса разрешения. Разработку двигаем по Scrumban, эпики не ломаем.
- **Владельца зовём только на итоговый «Пуш»** — когда накопились батчи (~10).
  Кратко: что вошло, статус QA, что готово к выгрузке. Плюс — на реальных
  развилках/блокерах, где нужно решение владельца (иначе не дёргаем).

## Процесс разработки

- Работать батчами: локально → QA после каждого батча → пуш **только по «Пуш»**
  от владельца.
- **Спека «как это должно работать» до реализации:** каждая фича/задача
  сопровождается кратким функциональным описанием (флоу, состояния, правила,
  крайние случаи, критерии приёмки) — как дизайн-док в `docs/*`. Согласуется с
  владельцем ДО кода. Без спеки не начинаем реализацию.
  Порядок: `brainstorming` → спека → `writing-plans` → план → исполнение.
  Правка очевидного бага по готовой спеке — исключение; новая функциональность,
  изменение поведения или переработка экрана — нет.
- **Интеграции — отдельная проработка логики ДО кода.** Каждая внешняя интеграция
  (форматы обмена, облако/синхронизация, магазин пресетов, платежи, аналитика,
  MIDI/аудио-устройства и т.п.) — это целостная логика, а не тонкая заглушка.
  По каждой — груминг через `vokal-product-agent` + дизайн-док
  `docs/INTEGRATION_*_DESIGN.md`: сценарии использования, подключение/авторизация,
  маппинг сущностей, направление и триггеры синхронизации, вебхуки/поллинг,
  идемпотентность, ошибки/ретраи, безопасность/секреты, крайние случаи, критерии
  приёмки + «Как проверить». Тайминг: груминг делаем **прямо перед сборкой каждой**
  интеграции, не пакетом заранее.
- **Ветки:** работаем в одной рабочей ветке, историю держим единой линией (без
  дублей от cherry-pick). Пуш — по «Пуш» владельца.
- **Промоушен (stage/prod) — отдельный процесс, владелец ведёт его сам.**
- Весь UI — только через дизайн-агента (`vokal-design-agent`) + UI-скиллы.
  Код/логика/тесты — через `vokal-development-agent` (реализация/ревью по
  спеке-доку). Итоговый QA и коммит-контроль — на мне.
- **Весь пользовательский текст — через связку копирайтинг → главред.** Любой
  текст, который видит пользователь (UI-микрокопи, уведомления, письма, контент
  сайта): (1) **копирайтер** (`vokal-copywriter`, скиллы `brand-voice`, `ux-copy`,
  `content-creation`/`draft-content`) пишет черновик; (2) **главред**
  (`vokal-editor-in-chief`, скилл `brand-review`) ревьюит: голос/тон бренда,
  ясность, единая терминология, грамотность РФ, отсутствие ложных обещаний и
  юр-рисков, консистентность. Итерация до «принято» — только потом текст идёт
  в макет/реализацию. Готовый текст = вход для дизайн-агента.
  Юр-чувствительный текст (оферта, согласия, политика ПДн) — через юриста,
  НЕ через главреда.
- **Секреты.** Никогда не коммитить токены, пароли, ключи, строки подключения.
  История git необратима. Всё чувствительное — в переменных окружения,
  в репозитории только `.env.example`.
- Юридические документы (`/legal/*`, версии согласий) — не трогать без явного
  согласования.

## Скиллы: когда какой

В `.claude/skills/` лежит набор superpowers-скиллов. Они не факультативны:
если скилл подходит к ситуации хотя бы на 1%, его надо вызвать ДО действия,
а не после. Точка входа — `using-superpowers`.

Порядок: сначала процессные скиллы (они задают подход), потом предметные
(дизайн, фронтенд, SEO и прочие).

| Ситуация | Скилл |
| --- | --- |
| Новая фича, компонент, изменение поведения | `brainstorming` — **до** любого кода и до планирования |
| Есть спека, нужен план многошаговой работы | `writing-plans` |
| Есть готовый план, исполняем | `executing-plans` (с чекпойнтами) или `subagent-driven-development` (в текущей сессии) |
| Пишем фичу или чиним баг | `test-driven-development` — тест до реализации |
| Баг, падающий тест, странное поведение | `systematic-debugging` — **до** предложения фикса |
| 2+ независимые задачи без общего состояния | `dispatching-parallel-agents` |
| Собираемся сказать «готово» | `verification-before-completion` — прогнать проверки, а не заявить на глаз |
| Крупная фича доделана | `requesting-code-review` |
| Пришло ревью | `receiving-code-review` — проверять, а не соглашаться из вежливости |
| Ветка готова к интеграции | `finishing-a-development-branch` |
| Работа требует изоляции от текущего дерева | `using-git-worktrees` |

Весь UI по-прежнему идет через `vokal-design-agent` + UI-скиллы, весь
пользовательский текст — через копирайтера и главреда (см. выше). Скиллы этот
порядок не отменяют, а дополняют.

**Артефакты процесса.** Спеки кладем в `docs/superpowers/specs/`, планы — в
`docs/superpowers/plans/`, дизайн-доки интеграций — в `docs/INTEGRATION_*_DESIGN.md`,
бэклог с оценками — в `docs/BACKLOG.md`.

## Груминг

Груминг — не разовое действие в начале, а постоянная часть цикла.

- **Перед каждым батчем** прогоняем бэклог через `vokal-product-agent`: WSJF,
  размер, ближайший слой, критерии приемки в формате «пользователь может X».
- **Перед каждой интеграцией** — отдельный груминг и дизайн-док
  `docs/INTEGRATION_*_DESIGN.md` прямо перед сборкой, не пакетом заранее.
- **После батча** возвращаемся в бэклог: что закрылось, что вскрылось, что
  переехало. Найденное в работе не держим в голове и не теряем — оно идет
  в бэклог с оценкой.
- Развилки, где нужно решение владельца, помечаем явно и не решаем молча за него.
- **Утверждения агентов о коде проверяем.** Груминг-агенты полезны в доменных
  рассуждениях и регулярно ошибаются в проверяемых фактах о репозитории: читают
  устаревшее состояние, считают на глаз, завышают проблему. Прежде чем заносить
  находку в бэклог или чинить по ней код, факт подтверждаем сами. Проверенное и
  опровергнутое пишем в раздел «Поправки груминга к фактам» в `docs/BACKLOG.md`,
  чтобы ошибка не тиражировалась следующей сессией.

## QA перед коммитом

Зелёные проверки перед каждым коммитом:

- типизация — `npm run typecheck`;
- тесты — `npm run test -- --run`;
- сборка — `npm run build`;
- пробелы/переводы строк — `git diff --check`.

Линтера в проекте нет; вместо него включены `noUnusedLocals` и
`noUnusedParameters` в `tsconfig.json` — они ловят код, который перестал
использоваться после правок (именно так однажды тихо пропала из интерфейса
оценка сложности обработки).

Если проверки ещё нет — так и писать, а не считать шаг пройденным.

**Правило про регрессы интерфейса.** Если правка меняет то, что пользователь
видит на экране, к ней идёт компонентный тест в `src/App.test.tsx`. Сервисные
тесты не ловят исчезнувший из вёрстки блок.

## Что лежит в репозитории

```
src/                 приложение: App.tsx, domain/ (типы и моки), services/ (моковые сервисы)
docs/                продуктовые документы, спеки и планы
.github/workflows/   CI: typecheck, тесты, сборка
.claude/skills/      115 навыков: разработка, дизайн, контент, SEO/Яндекс-стек, комплаенс
.claude/agents/      7 агентов проекта (vokal-*)
```

`.claude/skills/` весит около 60 МБ (в основном `gstack` с крупными тестовыми
фикстурами). Это наследство переноса из «Сальдо»; чистить — отдельным решением
владельца, к продукту отношения не имеет.

Скиллы и агенты перенесены из проекта «Сальдо»; саму «Сальдо»-специфику
(юрскилл, брендовые данные Директа) не переносили — вместо неё шаблоны.
