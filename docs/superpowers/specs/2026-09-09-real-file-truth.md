# Спека: правда о загруженном файле

Батч B4a. Груминг — `docs/BACKLOG.md`.

## Проблема

`createProjectFromUpload` в `src/services/mockServices.ts` клонирует демо-проект
целиком и подменяет у него только имя файла и настройки. Все музыкальные данные
остаются от чужой песни:

- тональность `G minor` и 104 BPM — от демо `Late Train Home`;
- аккордовая сетка — от демо;
- «точность разбора 83%» и проценты по партиям — от демо;
- длительность 214 секунд — константа в коде;
- качество исходника выводится из размера файла, а не из содержимого.

Пользователь загружает свою песню и видит разбор другой. Это прямое нарушение
поправки спеки от 2026-09-09: интерфейс не обещает точности, которой нет.
На демо-пути подмена помечена бейджем «демо-данные» и допустима; на своем файле —
нет.

## Что делаем

Файл перестает быть строкой имени. Браузер его декодирует, и проект получает
настоящие факты. Музыкальный разбор загруженного файла **отсутствует** и честно
называется отсутствующим, а не подставляется от демо.

Звук (волна, плеер, клик) — отдельный батч B4b. Здесь только правда о файле.

## Флоу

1. Пользователь выбирает файл. Проходит текущая валидация формата и размера.
2. Файл декодируется в браузере. Показывается состояние декодирования.
3. Успех: в проект попадают длительность, частота дискретизации, число каналов,
   размер. Качество исходника оценивается по содержимому.
4. Отказ декодера: файл отклоняется с причиной, отличной от «формат не
   поддерживается».
5. Проект создается с пустым музыкальным разбором.
6. На экране `Обзор` вместо тональности, BPM, аккордов и процентов — объяснение,
   что звук не анализируется.

## Состояния разбора

Вводится `SongAnalysis.source`:

- `demo` — данные подготовлены заранее, показываются как сегодня;
- `none` — разбора нет, показывается объяснение.

Промежуточных состояний нет: либо разбор есть, либо его нет.

## Правила

- Ни одно поле музыкального разбора не наследуется от демо при загрузке.
- Длительность берется из декодированного буфера, не из метаданных контейнера и
  не из константы.
- Качество исходника считается по содержимому: моно, низкая частота
  дискретизации, клиппинг. Правило `qualityForSize` удаляется.
- Файл не покидает браузер: сетевых вызовов при выборе и декодировании нет.
- Длительность выводится только в формате `мм:сс`. Формат «3 минуты 42 секунды»
  уронит сторож честности, и это не косметика, а условие зеленого CI.
- Вся работа с `AudioContext` — за интерфейсом с подставляемой реализацией:
  в jsdom этих API нет, иначе тесты нечем писать.

## Крайние случаи

- Файл не декодируется: битый MP3, ALAC внутри `.m4a`, DRM. Причина отказа
  отличается от «формат не поддерживается».
- Декодирование долгое: показывается состояние, повторный запуск заблокирован.
- Моно, 48 и 96 кГц, VBR MP3.
- Полная тишина или очень тихая запись: качество низкое, но это не ошибка.
- Файл нулевой длины.
- Пользователь выбирает второй файл во время декодирования.
- Демо-проекты остаются без изменений: у них `source: "demo"`.

## Критерии приемки

1. Пользователь выбирает файл — в блоке «Исходник» видны его настоящие
   длительность, формат, размер, частота дискретизации и число каналов.
   Тест: подставленный декодер на буфере 2 c / 44100 Гц / 2 канала дает эти
   значения; на экране `0:02`.
2. Загруженный проект не показывает чужой разбор. Тест сервисный: `analysis.chords`
   пуст, `confidenceByPart` пуст, `key` и `bpm` не равны демо-значениям.
   Тест компонентный: на вкладке `Обзор` нет процента точности и аккордовой
   ленты, есть объяснение.
3. Недекодируемый файл отклоняется с причиной, отличной от неподдерживаемого
   формата. Тест: декодер бросает — на экране роль `alert` с этой причиной.
4. Качество исходника считается по содержимому. Тест: моно 22050 Гц дает `low`,
   стерео 44100 Гц дает `medium` или `good`.
5. Демо-проекты не затронуты: разбор, аккорды и проценты на месте.
6. Сторож честности зеленый на всех экранах.
7. Сетевых вызовов при выборе файла нет. Тест на заглушках `fetch` и
   `XMLHttpRequest`.
