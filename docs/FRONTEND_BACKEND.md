# Фронтенд и сервер: как переключить и чем проверить

Батч «фронт-клиент». Документ описывает слой доступа к серверу на стороне
фронтенда: как включить работу против настоящего API, что для этого должно
быть поднято, чем убедиться, что все работает, и что происходит, когда не
работает.

**Состояние на момент написания.** Экраны по-прежнему берут данные из
`src/services/mockServices.ts` напрямую. Слой ниже собран и покрыт тестами, но
переезд экранов на него — отдельная задача: `src/App.tsx` принадлежит другому
батчу. Пока переключатель влияет только на код, который явно позвал
`getBackend()`.

## Переключатель

Один признак, одна переменная:

| `VITE_API_BASE` | Что происходит |
| --- | --- |
| пусто или не задана | Работают моки. Сеть не трогается вовсе. |
| задана | Работает сервер. Все обращения идут по этому адресу. |

Адрес указывается **вместе с префиксом `/api`**: клиент дописывает к нему
пути контракта (`/projects`, `/uploads/constraints`). Допустим и
относительный путь, если фронтенд и API стоят за одним доменом.

```bash
# в корне репозитория
cp .env.example .env.local
# и вписать адрес
echo 'VITE_API_BASE=http://127.0.0.1:8000/api' >> .env.local

npm run dev   # перезапуск обязателен: Vite читает переменные при старте
```

Прежнее имя `VITE_API_BASE_URL` читается как запасное, чтобы уже настроенный
локальный `.env` не замолчал. В новых настройках используется `VITE_API_BASE`.

Заданное, но неразбираемое значение (`VITE_API_BASE=не адрес`) **роняет
сборку клиента с внятным сообщением**, а не откатывается на моки. Тихий откат
— самая дорогая из возможных ошибок: разработчик уверен, что смотрит на
сервер, а видит подготовленные данные.

Секретов среди переменных фронтенда нет и быть не может: все, что начинается
на `VITE_`, попадает в собранный бандл. Ключи провайдеров, строка подключения
к базе и доступы к хранилищу живут только на бэкенде — `server/.env.example`.

## Что должно быть поднято

1. **PostgreSQL 16** с базой, указанной в `VOKAL_DATABASE_URL`. Без нее
   `/ready` отвечает `503`, а адреса, которым нужна база, — отказом.
2. **Сервер FastAPI**: из каталога `server/`, в его виртуальном окружении.

   ```bash
   vokal-dev
   # то же самое руками:
   uvicorn app.main:create_app --factory --reload --host 127.0.0.1 --port 8000
   ```

3. **Роутеры API подключены** в `app/main.py`. На момент написания там стоит
   место подключения с комментарием, а сам `include_router` закомментирован:
   роутеры приносит другой батч. Пока это так, любой адрес `/api/...`
   отвечает `404` в общем формате ошибки — это видно сразу (см. проверку 2).
4. **CORS** разрешает адрес фронтенда. По умолчанию сервер уже разрешает
   `http://127.0.0.1:5173` и `http://127.0.0.1:4173` (dev-сервер и
   предпросмотр сборки). Другой адрес добавляется в `VOKAL_CORS_ORIGINS`.

## Чем проверить

```bash
# 1. Сервер жив, заголовок запроса возвращается
curl -i http://127.0.0.1:8000/health

# 2. Роутеры подключены? 404 — еще нет, 501 — уже да
curl -i http://127.0.0.1:8000/api/uploads/constraints

# 3. Слой доступа на фронтенде цел
npm run test -- --run src/services/api
```

Что означают ответы на проверке 2:

| Ответ | Что это значит |
| --- | --- |
| `404 not_found` | Роутеры еще не подключены к приложению. |
| `501 not_implemented` | Адрес объявлен, реализации нет. В `details.missing` сказано, чего не хватает. Это **нормальное** состояние текущего этапа. |
| `200` | Адрес работает. |

Отдельно: `501` — не ошибка клиента и не поломка. Сервер честно говорит, что
этой части еще нет, и перечисляет недостающее. Клиент доносит это до
вызывающего кода как отказ с кодом `not_implemented`; проверяется помощником
`isNotImplemented(failure)`.

## Из чего собран слой

| Файл | Зачем |
| --- | --- |
| `src/services/api/config.ts` | Переключатель источника: разбор `VITE_API_BASE`. |
| `src/services/api/errors.ts` | Типизированный результат: сеть, сервер, схема, отмена, неподдерживаемая операция. |
| `src/services/api/decode.ts` | Проверка ответа на соответствие контракту в рантайме. |
| `src/services/api/contract.ts` | Форма провода: типы и проверки из `server/app/api/schemas/*`. |
| `src/services/api/http.ts` | Один запрос: заголовки, срок ожидания, отмена, классификация отказа, повторы. |
| `src/services/api/client.ts` | Клиент по контракту: один метод — один адрес. |
| `src/services/api/poll.ts` | Опрос статуса задания обработки. |
| `src/services/api/upload.ts` | Отправка файла в хранилище с прогрессом. |
| `src/services/api/mapping.ts` | Перевод формы провода в доменную модель фронтенда. |
| `src/services/backend.ts` | Фасад: вызывающий код не знает, моки это или сервер. |

Экранам нужен только фасад:

```ts
import { getBackend } from "./services/backend";

const backend = getBackend();          // моки или сервер — по переменной окружения
const result = await backend.getProject(projectId);

if (!result.ok) {
  // разбор отказа, см. таблицу ниже
  return;
}
result.data.project;  // доменный Project из src/domain/types.ts
result.data.extras;   // то, что домен пока не умеет выразить
```

## Ошибки: пять видов, ни одного молчаливого

Ни один вызов не бросает исключение наружу и не возвращает `undefined`.
Результат всегда `ApiResult<T>`: либо `ok`, либо `error` одного из видов.

| `kind` | Когда | Что делать вызывающему |
| --- | --- | --- |
| `network` | До сервера не дошли: обрыв связи (`reason: "fetch_failed"`) или молчание дольше срока (`reason: "timeout"`). | Предложить повторить. Данные не изменились. |
| `http` | Сервер ответил отказом. Есть `status`, машинный `code`, `requestId` и `details`. | Ветвиться по `code`. Повторять бессмысленно. |
| `schema` | Ответ не соответствует контракту. В `path` — поле, на котором разошлось. | Чинить код или контракт. Пользователю показывать «версии разошлись», а не «нет связи». |
| `aborted` | Запрос отменен вызывающим или сроком ожидания страницы. | Ничего. Это не сбой. |
| `unsupported` | Источник такой операции не умеет. В `missing` — чего именно не хватает. | Показать честное «этого еще нет», перечислив недостающее. |

Тексты в поле `message` — диагностика для разработчика и логов. На экран они
не годятся: пользовательский текст идет через связку копирайтер — главред
(CLAUDE.md), и на момент написания этих формулировок еще нет.

`requestId` приходит из заголовка `X-Request-ID` и из тела ошибки. По нему
поддержка находит след в логах сервера — его стоит показывать рядом с
сообщением об ошибке.

## Повторы

Повторяем **только сетевые сбои** — то, что до сервера не дошло. Ответ
сервера, даже `500`, не повторяем: сервер уже отработал запрос, и вторая
попытка может сделать работу дважды.

Правило по методам:

- `GET` — повторяем всегда;
- любая запись — **только с ключом идемпотентности** (`Idempotency-Key`).

Без ключа повтор `POST` — это второй проект, второе задание в очереди и второе
списание стоимости. Сервер принимает заголовок ровно для этого. Ключ задается
в `options.idempotencyKey`; фасад проставляет его сам там, где знает, из чего
собрать устойчивое значение (создание проекта из загрузки, подтверждение
загрузки, обе операции удаления).

Задержка растет вдвое от 300 мс, с ограничением сверху и разбросом: без
разброса все вкладки, потерявшие связь одновременно, возвращаются к серверу
тоже одновременно. Политика меняется на вызов: `{ retry: false }` или
`{ retry: { attempts, baseDelayMs, maxDelayMs, factor } }`.

`DELETE` не повторяется без ключа намеренно: по букве HTTP он идемпотентен, но
у нас гасит выданную ссылку и пишет строку в аудит-лог.

## Опрос задания обработки

```ts
const started = await backend.startProcessing(projectId, { idempotencyKey });
if (started.ok) {
  const finished = await backend.watchProcessing(started.data.jobId, {
    signal: controller.signal,
    onUpdate: (job) => setProgress(job.progressPercent),
  });
}
```

- пауза между вопросами берется у сервера (`pollAfterMs`), а не выбирается
  клиентом: иначе интервал становится случайной константой в интерфейсе;
- опрос останавливается на завершении задания, на отказе сервера, на отмене и
  по пределу числа вопросов;
- одиночные обрывы связи переживаются (по умолчанию до пяти подряд), затем
  возвращается сетевой отказ;
- **`ok` означает «задание дошло до конечного состояния», а не «получилось»**.
  Упавшее задание — это `ok` со статусом `error` и кодом в `errorCode`.
  Помощники: `isJobTerminal`, `isJobFailed`.

## Загрузка файла

`backend.uploadFile(file, { onProgress, signal })` делает три шага: заявка на
загрузку, отправка файла **прямо в хранилище** по выданной ссылке,
подтверждение приема. Файл не проходит через процесс API — иначе каждая песня
занимала бы его на все время передачи.

Прогресс отправки измеряется через `XMLHttpRequest`: у `fetch` события
прогресса отправки нет, а полоса, которая не двигается на файле в десятки
мегабайт, читается как зависший интерфейс. В среде без `XMLHttpRequest`
операция честно отказывает (`unsupported`), а не сообщает об успехе.

## Отмена

Любой вызов принимает `signal`. Отмена дает отдельный вид отказа (`aborted`) и
никогда не выглядит как сбой сети: иначе пользователь получит «нет связи»
там, где он просто ушел с экрана.

```ts
const controller = new AbortController();
const result = await backend.getProject(id, { signal: controller.signal });
// ...
controller.abort();
```

Срок ожидания одного запроса — 15 секунд по умолчанию, меняется через
`options.timeoutMs`. Истекший срок дает `network` с `reason: "timeout"`.

## Где контракт и домен расходятся

Расхождение осознанное и описано на стороне сервера
(`server/app/api/schemas/enums.py`): в контракте — устойчивые латинские ключи,
в `src/domain/types.ts` на тех же местах стоят русские подписи. Перевод живет
в `src/services/api/mapping.ts` таблицами, а не разбором строк.

Есть места, где доменная модель фронтенда **не умеет** выразить ответ сервера.
Там значение не подменяется похожим, а уезжает в `extras` рядом с проектом:

| Что | Контракт | Домен | Как сейчас |
| --- | --- | --- | --- |
| Состояние загрузки | `awaiting_file`, `stored`, `rejected`, `purged` | нет поля | `extras.uploadState` |
| Состояние удаления | `present`, `purge_requested`, `purged`, `purge_failed` | булево «удалено» | `extras.sourceState`, `extras.resultsState` |
| Статус выданной ссылки | `active`, `stale`, `revoked`, `expired` | `mock_created`, `stale` | `extras.shareLinks`, доменный список пуст |
| Код ошибки задания | `errorCode` | нет поля | `extras.jobErrorCode` |

Последние два — не мелочь. Показать отозванную ссылку рабочей значит нарушить
обещание `docs/DELETION_AND_RETENTION_DESIGN.md`, а показать «удалено» до
подтверждения хранилища — сказать неправду о необратимой операции. Поэтому
доменный список ссылок остается пустым до правки `src/domain/types.ts`, а не
заполняется приблизительно.

У моков `extras` заполнены `null`: моковый источник этих состояний не знает и
не делает вид, что знает.

## Что источники честно не умеют

| Операция | Моки | Сервер |
| --- | --- | --- |
| `uploadFile` | отказ: хранилища нет, файл остается на устройстве | работает по контракту |
| `startProcessing`, `watchProcessing` | отказ: обработки звука нет | работает по контракту |
| `addSessionNote` | работает | отказ: адреса в контракте нет |
| `createProject` | работает | нужен идентификатор принятой загрузки и типизированная настройка |
| `applyDirectorAction` | работает | нужна базовая версия (`baseVersionId`) |

Отказ всегда называет, чего не хватает — так же, как это делает сервер в
`501`. Правдоподобных выдумок вместо ответа нет ни в одном источнике.

## Проверки этого слоя

```bash
npm run typecheck
npm run test -- --run src/services/api   # 50 проверок слоя
npm run test -- --run                    # весь фронтенд
npm run build
```

Тесты идут на подмененном `fetch` в окружении `node`: настоящий сервер для них
не нужен. Покрыто: успех, обрыв связи, отказ сервера, отказ не в формате
конверта, несоответствие схемы, не-JSON в успешном ответе, срок ожидания,
отмена, повторы (включая запрет повтора записи без ключа), опрос задания во
всех исходах, загрузка с прогрессом, перевод ключей контракта в подписи
домена, честные отказы обоих источников.
